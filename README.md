# Polymarket 体育扫尾盘交易系统

一个面向 Polymarket 体育胜负盘的低延迟交易与验证系统。系统组合公开体育比分、Polymarket 实时体育流、Gamma/CLOB 市场数据和账户 API，在比赛接近结束时识别高确定性机会，并通过独立的风控、模拟盘、实盘执行、对账和 Dashboard 链路完成交易闭环。

> 本文档面向希望复用本项目资产的开发者与 Agent。文档基线为 `2026-11-12`，代码行为优先于历史文档；发生冲突时请同时检查 `src/` 和 `PROJECT_DESIGN.md` 的最新条目。

## 项目概览

核心交易假设：

```text
公开比分事件已经表明比赛大概率确定
        -> Polymarket 价格尚未完全收敛
        -> 快速识别、匹配市场和检查盘口
        -> 通过限价单买入领先方 YES
        -> 等待比赛结算或价格向 1.00 收敛
```

项目不是链上 MEV，也不使用非公开信息。主要研究对象是：

- 体育比分源到 Polymarket 价格之间的时间窗。
- 多来源比分校验、实时推送覆盖和轮询兜底。
- 市场匹配、盘口深度、价格区间和执行成本。
- 小资金实盘下的风控、账本口径、订单对账和异常恢复。

## 已落地能力

### 信号与数据

- 3 秒级轮询 ESPN/MLB 官方数据，并用 Polymarket 体育 WebSocket 推送加速。
- 推送数据必须先与轮询源逐队对齐比分口径；未对齐、回退、过期或冲突时自动退回轮询源。
- 事件驱动信号处理与主循环兜底并存，避免只在固定轮询点发现状态变化。
- 队名/缩写归一化、唯一匹配保护、网球逐盘局分解析、CS2 回合比分解析。
- 数据源健康度区分“无比赛”“数据偏旧”“重试中”“异常”，并展示源、耗时和覆盖状态。

### 市场与执行

- Gamma 市场搜索、Polymarket outcomes/token 匹配、CLOB best bid/ask 和订单簿读取。
- 入场价格上下限、最低/最高价格、盘口年龄、价差、单边盘、空深度和交叉盘保护。
- 模拟盘与实盘并行，使用相同市场信号但维护独立账本。
- 实盘支持全局开关、无人值守开关、密码和确认短语、全局停止与重启后安全恢复。
- 下单前写审计事件，订单状态、成交、撤单、错误和结算均可追踪。
- 以交易所成交明细回填真实均价；maker 与 taker 成交分别统计，防止把其他 maker 的成交量记到本地订单。

### 账户、结算与持久化

- 账户余额、持仓、活动订单、成交和已结算仓位的只读监控。
- 本地账本与交易所账本分别展示，避免把模拟盘净值和实盘余额混为一谈。
- 已结算、待入账、已赎回和亏损归零等场景有独立口径。
- 模拟盘结算支持比分流即时结算和 Gamma 市场结算兜底。
- 状态文件采用原子写入；JSONL 追加账本支持体积轮转、重启恢复和重复事件去重。

### 研究与可观测性

- 回测、参数网格搜索、阈值校准、赔率/ROI 分档和样本外复盘工具。
- 网球模型账本、MLB 数据集与逻辑回归、足球双泊松模型、MLB 局面采集、CS2 决胜图影子仓。
- API-Tennis 逐分延迟赛跑、CLOB Book WebSocket 高频路径、MFE/MAE 和止盈止损回放。
- Dashboard 集中展示数据健康、信号拒绝原因、延迟、影子仓、收益曲线和执行状态。

## 已验证结果

### 工程成果

- 实盘链路已在 VPS 上运行，覆盖下单、成交、撤单、账户对账和结算。
- VPS 迁移实测显著降低延迟：认证探活约 `406 ms -> 40 ms`，Gamma 约 `2227 ms -> 28 ms`，完整 `/book` 读取约 `1170 ms -> 35~56 ms`。
- Polymarket Data API v1 下线后已迁移到 v2，并适配游标分页和 snake_case 字段。
- 修复过订单金额下限、余额小数换算、盘口采集方向、待入账亏损隐藏、maker 成交量归属和模拟盘账本错位等生产问题。
- 研究数据改为带时间戳轮转，避免固定 `.1` 文件互相覆盖。

### 经济结果

实盘已经真实运行，但样本、资金和策略版本多次变化，不能把短期收益当成稳定 edge。

文档记录的 `2026-10-13` 至 `2026-10-19` 实盘样本为 102 笔、胜率 `92.2%`、PnL `+$0.50`、ROI `+0.22%`；相邻两周合计 199 笔、PnL `-$1.18`、ROI `-0.29%`。此前所谓 `+6.68%` 的收益后来被修正为约 `+1.2%`，说明真实成交价、待入账结算和账户口径会显著改变结论。

因此当前判断是：系统已经具备研究和执行价值，但还不具备根据历史胜率扩大仓位的证据。多个实验都表明，高胜率主要来自高价买入的机械赔率，而不是稳定跑赢市场。

### 研究结论

| 方向 | 结果 | 是否进入生产 |
|---|---|---|
| MLB 逻辑回归 | AUC 最高约 `0.952`，但仍未打赢“直接用市场价”的基线；模型主要用价格派生特征重新推导价格 | 否，仅研究 |
| 网球胜率模型 | 总体校准接近市场，但模型边际与 ROI 不单调，多个正边际组反而亏损 | 否，仅记录和复盘 |
| 足球双泊松模型 | 5,868 场半场样本上 Brier `0.1742`，优于仅用基准率的 `0.2457` | 是，用于足球锁定判定 |
| 入场价格区间 | 历史实盘样本中 `<0.90` 与 `>=0.97` 两端偏弱，`0.90~0.97` 相对更好 | 作为风控闸门使用，仍需更多样本 |
| 固定价格止损 | 4,082 条触发、3,918 条可匹配结算记录；追价口径下所有组合均为负 | 否，已从主要 UI 移除 |
| API-Tennis 抢跑 | 事件后波动明显，但有利/不利振幅接近对半，未形成稳定方向 edge | 否，仅影子仓和延迟研究 |
| 足球事件反应 | 进球后 120 秒朝进球方变化比例仅约 `53%`，未观察到稳定快速收敛 | 未购买付费源，继续观察 |

这些结论的共同指向是：当前更值得复用的是数据、执行、风控和审计基础设施；单纯增加胜率模型或提高仓位没有得到证据支持。

## 推荐优先复用顺序

如果另一个 Agent 的目标是构建新的 Polymarket 事件交易项目，建议按以下顺序复用：

1. `src/sports_overlay.py`：复用“先校验、再加速、异常回退”的多数据源安全模式。
2. `src/live_trader.py`、`src/atomic_io.py`、`src/live_account.py`：复用执行安全、审计和交易所对账。
3. `src/polymarket_feed.py`、`src/clob_book.py`：复用市场匹配、token 解析和盘口结构。
4. `src/paper_trader.py` 与 `src/settlement_*`：建立独立模拟账本和结算闭环。
5. `tools/measure_chain_latency.py` 与 `tools/latency_report.py`：先测量链路，再讨论策略。
6. Dashboard 和研究账本：最后接入，避免把 UI 或实验逻辑耦合进核心交易链路。

如果目标是复用“盈利策略”，需要更谨慎：当前仓库能提供规则、数据管线和验证方法，但不能提供已被统计证明的稳定 alpha。复用时应先复现数据口径，再跑独立样本外验证，并计入手续费、滑点、盘口深度和未成交概率。

## 快速启动

```powershell
pip install -r requirements.txt
Copy-Item .env.example .env
python -m src.main
```

启动后访问：

- 首页：`http://127.0.0.1:8082`
- 风控设置：`http://127.0.0.1:8082/settings`
- 概率盘：`http://127.0.0.1:8082/probability`

切换到实盘前至少需要：

1. 在 `.env` 中配置钱包和 Polymarket API 凭据。
2. 配置强随机 `LIVE_MODE_PASSWORD`。
3. 确认 `LIVE_EXECUTION_ENABLED`、`LIVE_GLOBAL_ENABLED`、允许运动和限额。
4. 先完成只读账户验证、干跑和最小金额测试。
5. 阅读 `PROJECT_DESIGN.md` 第 10、13、15 节。

## 安全与当前边界

- `.env`、私钥、API key、日志和交易账本不进入 Git。
- 默认模式为 `paper`；实盘需要总开关、执行开关、无人值守开关、密码和确认短语。
- 实盘只适合极小资金验证，不应根据短期胜率扩仓。
- `LIVE_GLOBAL_ENABLED=0` 是总闸；全局停止会撤销活动订单并阻止重启后自动恢复实盘。
- 数据源异常时优先退化为轮询，不使用未校验推送下单。
- 市场匹配失败、盘口过旧、价差异常、深度不足和超过价格区间均应拒绝交易。
- 当前没有完整托管在仓库中的自动化测试套件，关键测试多数位于未提交的 `tmp/`。
- 当前没有自动仓位优化，也没有被证明可持续的强概率模型。
- 历史回放、影子仓和模拟盘结果都不能替代真实成交验证。

## 已知限制

1. 体育数据存在多源命名、时序和比分格式差异，市场匹配仍可能返回 `NO_MARKET` 或 `NO_TOKEN`。
2. Tennis 对发球权、伤退、场地等上下文建模不足，模型多次复盘未达到生产闸门标准。
3. CS2、足球和网球等短窗口策略对延迟极敏感，成交前价格可能已移动。
4. 回测通常高估成交质量，真实执行受滑点、盘口深度、手续费和部分成交影响。
5. 实盘表现受策略版本、资金规模和样本期影响，当前经济结论不足以支持扩容。
6. 运行数据和训练集未纳入仓库，Agent 不能直接复现全部历史指标。
7. Dashboard 和主调度文件较大，继续扩展前建议拆分模块和补齐持久化测试。

## 仓库内容边界

仓库当前提交：

- `src/`：生产主链路、信号、数据、执行、账本和 Dashboard。
- `tools/`：部署、延迟测量、校准、复盘、研究采样和 systemd 服务。
- `*.md`：设计、产品与迁移文档。
- `.env.example`、`requirements*.txt`：配置样例和依赖。

仓库不包含：

- `.env`、私钥、API key、cookie 和本地凭据。
- `logs/`、`trades/`、`tmp/`、`tmp_py_clob_client/`。
- 交易数据、模型训练集、预测明细、影子仓账本和历史日志。
- 大多数位于 `tmp/` 的离线测试与一次性探针。

## 复用结论

本项目最有价值的资产是：

1. 多源体育数据的安全融合方式。
2. Polymarket 市场匹配与盘口解析。
3. 小资金实盘执行、风控、审计和对账基础设施。
4. 影子仓、高频路径和事件级链路的验证方法论。
5. 对“模型未证明优于市场”的负面结论与可复现实验思路。

最不应直接复用的是：未经样本外验证的交易阈值、历史回测收益率、短期实盘胜率，以及把推送数据直接替换轮询数据而没有校验的设计。
